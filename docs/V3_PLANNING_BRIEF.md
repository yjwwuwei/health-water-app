## 旧用户与数据迁移约束

以下内容应进入方案和验收，不应在实现末尾补做：

- 旧数据只有每日汇总，不能凭空恢复逐笔时间。设计明确的历史汇总表示，并保留原始数据与可重入的迁移标记。
- 旧数据使用 UTC 日期键，缺少逐笔时间时无法无歧义地还原本地日期。规划迁移策略，避免整体移动日期后丢失原始语义。
- 旧本地数据没有账号归属。不要自动假定全部属于接下来登录的账号；设计游客数据保留和认领流程。
- 数据库迁移应具备事务、备份、失败恢复及版本兼容策略；回滚界面代码不必然能回滚已变更的数据格式。
- 核实旧 APK 的应用 ID、签名、版本号和 WebView 存储 origin。避免通过卸载重装、变更包名或 scheme 绕过升级问题而损失用户数据。
- 账号切换、未完成同步、撤销后的删除标记、多端离线修改和重复提交需要独立验收场景。
- 仓库内没有完整可部署的 Firestore Rules，不能从前端代码推定生产权限或宣布已有数据泄露。

- 本轮没有为规划安装 JDK、Android SDK 或修改系统环境变量。

## 需要在计划中收敛的关键决策

只对会改变范围或架构的问题询问用户；其他实现细节给出推荐及依据。

1. **主要交付平台与使用人群。** 建议先明确 Android 为主还是 Android 与 Web 同等验收，以及主要使用网络环境。
2. **首版是否必须恢复多端云同步。** 比较离线记录加导出与保留 Firebase 同步的首版成本；若提出替换后端，需要可核实的收益与迁移代价。
3. **排行榜和姿势打卡的定位。** 建议作为可延期功能评估，说明保留、隐藏或移除对已有用户的影响。
4. **视觉与交互方向。** 可以重做，但优先解决主操作、记录反馈、历史编辑和提醒控制；避免先投入完整视觉稿再确定页面范围。

许可证需要维护者最终选择；在选择之前不要擅自添加法律授权。具体目标饮水量也不应被当成适用于所有人的固定医学结论。

## 计划模式的预期交付

形成一份决策明确的 v3 计划，覆盖首版范围、延期项、页面流程、架构与数据模型、同步及权限、迁移、分阶段改动、风险与回退、自动化和真机验收。每一阶段写出可观察的完成条件。

建议首先规划可启动、可靠记录和数据安全的最小版本，再安排提醒与历史体验，以及最终决定保留的云端和实验功能。实施顺序需按最终依赖关系调整。

不要为了形成计划先修完所有旧缺陷，也不要把环境阻断当成无法分析代码的理由。不要直接运行会批量暂存并推送全部文件的 `npm run push`。
